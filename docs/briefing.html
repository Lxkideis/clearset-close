01 / Problem and system design

The lab reconciles expected financial events against processor activity, payout membership, signed platform movements and independent bank credits. It preserves source revisions and separates financial findings from the investigation and review workflow.

Data contractsValidate money precision, currency, timestamps and source keys before atomic import.Seven pinned synthetic source contracts.
SQL controlsCompare gross, fee and net independently; aggregate before joins; quarantine duplicates; calculate currency balance bridges.Small local fixture with intentional defects.
Evidence and replayRecord source, policy and code fingerprints; select revisions by knowledge cutoff; preserve immutable snapshots.Replay only the evidence supplied to the lab.

PostgreSQL supports exact integer/numeric arithmetic, JSONB lineage, window functions and transaction controls. A MySQL port would require equivalent join, ingestion and locking behavior; it has not been implemented or validated.

Exact accepted columns and types live in src/contracts.py. They are strict pinned subsets, not a complete Stripe schema. Format/precision failures reject a whole packet; economically inconsistent but parseable rows are retained as visible control failures. SGD/USD use two decimals; JPY uses zero. No FX conversion.

03 / Clocks and correction model

The business interval is 1 October 2026 00:00 SGT inclusive through 21 October 00:00 SGT exclusive. The same business period is restated at 10:00, 11:00 and 12:00 SGT knowledge cutoffs. Financial effective time, simulated source observation time and actual system ingestion time are stored separately.

  1. Validate all files before opening the import transaction; use a transaction-level advisory lock for a consistent packet/snapshot boundary.
  2. Append observations keyed by source, business key and revision. Corrections and retractions are new versions; prior observations remain.
  3. For a cutoff, select the highest revision known at that instant before filtering retracted records. This prevents old data from reappearing.
  4. Fingerprint canonical UTC period/cutoff, active and retracted selected versions, policy and engine code. An identical input replays the same immutable snapshot.
  5. Keep lookback activity for payout membership. Transactions outside the business interval do not enter period activity; prior activity can still belong to a current payout batch.

Observation/revision metadata is the lab's adapter envelope. It is not claimed to be a Stripe-provided correction API. Snapshot history is finite evidence supplied to this system, not proof that all external events were received.

04 / Financial design choices

Failure modeControl and reasoning
Matching net hides bad componentsGross and fee are checked independently. A +5 gross and +5 fee error leaves net unchanged but is still blocked.
Many-to-many joins inflate sumsAggregate ledger/activity at business-key grain and membership/movements/bank at payout grain before joining. Duplicate business keys and bank references are blocked.
Same amount looks like a bank matchExact reference, currency, amount and uniqueness are required. Same-amount candidates are suggestions only; the fixture deliberately includes two candidates.
Wrong currency produces a misleading deltaNo numeric cross-currency transaction delta is reported. Controls remain currency-specific and no global monetary total is shown.
Bank booking lags report arrivalEstimated arrival, report availability and bank booking are different clocks. A configurable investigation grace distinguishes pending from overdue; weekends and supplied holidays only.
Failed payout counted as a normal cash outflowWithdrawal and reversal net to zero; no bank credit is expected for failed/canceled payouts. Missing reversal is a blocker.
Manual payout assigned arbitrarilyAutomatic membership is not inferred for manual payouts. Platform and bank movement checks still apply.
Fees are counted twiceThe bridge uses signed movement net once. Nonzero payout movement fees are explicitly unsupported and block close; not silently ignored.
Misleading average fee ratesUse total observed fees / total charge gross × 10,000 over unique comparable charges. Refunds/disputes excluded. Coverage and fictional schedule status are explicit.
Old unallocated balance called cash lossAging uses availability time, separating not-yet-available from matured unallocated activity. The latter is an investigation advisory, not a proven loss.

05 / Evidence, persistence and operational controls

Import batches record file SHA-256 and both observation and actual ingestion timestamps. Observations reference batches. Close runs reference a code hash, policy and source fingerprint; control results reference each run and source observation IDs. Notes and reviewer certifications are separate append-only records.

Application grants prohibit observation updates and deletes; database triggers also reject mutation. A completed run cannot be updated. This guards the application's audit history but a database owner/superuser can administer the system; no cryptographic tamper-proof ledger is claimed.

Certification requires a separate reviewer, zero blocking findings, no newer supplied source evidence, and an unchanged fingerprint. A note is documentation only and never changes financial status. The local visible demo tokens are replaceable environment variables, not production access control. Do not expose this loopback demo publicly.

06 / Validation and reproducible outputs

The independent fixture generator starts with economic events, calculates per-currency balances in Python, then emits intentionally defective extracts plus correction packets. Thirteen named initial failures have explicit expected outcomes. Real PostgreSQL integration tests check balances, ambiguity, precision, concurrency, rollback, history, permissions and the API.

Recorded main fixture: 3,000 bulk charges plus refunds, disputes, reversals and boundary cases. Initial 31 blocking findings → source corrections 6 → bank corrections 0. Four pending results and one advisory remain. These are correlated control results, not 31 unique transactions. All finance memo amounts are generated from persisted results, not copied from expected answers.

artifacts/publication-verification.json records the verified test count and publication checks. benchmark.json records seven measured full snapshot executions after one warm-up, excluding ingestion. The workload is small and local. transaction_query_plan.json gives an actual PostgreSQL execution plan. These do not support production throughput or savings claims.
